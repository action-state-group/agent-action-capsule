# x402 Adapter Declaration — v0

**Status.** Informational adapter declaration, kept in this repository. It is not part of any
Internet-Draft revision and changes no posted draft. It declares, for x402 payment objects, the
five items an adapter for a foreign object declares: (a) the native object and its format, (b) the
issuer's identity and how the relying party's trust policy resolves it, (c) the native verification
method, (d) the exact predicate the adapter can support, and (e) the per-property result and the
method that produced it. Its conformance vectors are in `vectors/adapters/x402/` (§9).

The adapter applies the as-transmitted rule of the Minimum Evidence Interoperability Profile
(`spec/interop-profile-v0.md` §5.1, "A foreign signed object") and the wrapping rules of
`draft-mih-agent-settlement-records-00` (Wrapping Existing Signed Objects, Wrapped Object Types).
It changes neither. Carrying an x402 object by digest proves possession of its octets and nothing
more. A verifier runs the checks below before it reports any property of the object's signature or
meaning (profile §7.2 `native_check`, P-11).

Items marked **TO-CONFIRM** depend on a recorded Base Sepolia (`eip155:84532`) payment that this
revision has not yet been checked against. Each is stated from the public x402 specification and
will be confirmed or corrected against that recording. Until then the vectors are constructed, not
recorded (§9).

## 2. The answer in brief

An x402 payment carries up to three objects. Exactly one is always signed:

| Object | Wire location (HTTP, v2) | Signed? | Signed by |
|---|---|---|---|
| `PaymentPayload` | `PAYMENT-SIGNATURE` request header | **yes**: the scheme payload carries the payer's signature over an EIP-3009 transfer authorization | payer |
| `SettlementResponse` | `PAYMENT-RESPONSE` response header | **no** | — (produced by the facilitator, delivered by the resource server) |
| Receipt (Offer and Receipt Extension) | inside the `SettlementResponse`, at `extensions["offer-receipt"].info.receipt`; present only when the server uses the extension | **yes** | resource server (payee) |

The settlement response is not natively signed. For it, this adapter supports possession and
transport-level provenance only (§6.2). Facilitator identity is therefore not cryptographic. What
the response says about settlement is checked against the chain it names, by transaction lookup.
That lookup is an independent source, not a check of the facilitator's statement. §8 names what
x402 would need to add for a native check.

The receipt is its own wrapped object (`x402.receipt`) with its own issuer, the payee. It is not a
property of the settlement response that carries it.

The `PaymentRequired` object (`PAYMENT-REQUIRED` response header) is not signed either. A signed
offer from the Offer and Receipt Extension is the payee's signed statement of terms. It is
registered as `x402.offer` and is outside this revision's predicates (§10).

## 3. Scope of v0

| Dimension | Supported in v0 | Otherwise |
|---|---|---|
| x402 version | `x402Version` 2 | 1: noted (§3.1), `NOT_CHECKED` |
| Scheme | `exact` | any other: `NOT_CHECKED` |
| Network | `eip155:*` (CAIP-2), including Base Sepolia `eip155:84532` and Base `eip155:8453` | any other namespace: `NOT_CHECKED` |
| Asset transfer method | `eip3009` (explicit, or absent: the scheme's default) | `permit2`: `NOT_CHECKED`. `erc7710`: possession only (FR-20); the payment's authority is a delegation redeemed on chain, not a payer signature this adapter checks, so `payer_signature` is `NOT_CHECKED` |
| Payer signature | 65-byte secp256k1 ECDSA signature (scheme Phase 1: "the 65-byte signature") | any other length, including contract-account signatures: `NOT_CHECKED` |
| Payment flow | `authorization` (verify, resource, settle) | `upfront`, `escrow`: the objects are the same; ordering is not a property this adapter checks |
| Receipt | payload version 1, EIP-712 format; payload version 2, EIP-712 format, under each of the two open proposals (§6.3) | JWS format, and any other payload version: `NOT_CHECKED` |

`NOT_CHECKED` here means the input is present and the verifier did not run the check because the
method is unsupported (profile §7.1). It never reads as a failure of the object.

### 3.1 x402 version 1

Version 1 carries the payment payload in the `X-PAYMENT` request header and the settlement
response in `X-PAYMENT-RESPONSE`, both base64-encoded JSON. Its payload puts `scheme` and `network`
at the top level and names networks by string (for example `base-sepolia`), not CAIP-2. The
EIP-3009 `payload` member (`signature`, `authorization`) has the same shape as in version 2. This
revision reports a version 1 object as `NOT_CHECKED` (unsupported version). The registered octet
definition of `x402.payment-payload` names the `PAYMENT-SIGNATURE` header only, and that of
`x402.settle-response` names `PAYMENT-RESPONSE` only (Open point A-1, §11).

## 4. (a) Native objects and their formats

All three objects are JSON. None defines a canonical byte form. The octets digested and carried
are the ones the registered wrapped object type names (`draft-mih-agent-settlement-records-00`,
Wrapped Object Types). These are never parsed and re-serialized before digesting.

| Object | Wrapped object type | Octets |
|---|---|---|
| `PaymentPayload` | `x402.payment-payload` (issuer: payer) | the base64-decoded value of the `PAYMENT-SIGNATURE` header as sent |
| `SettlementResponse` | `x402.settle-response` (issuer: facilitator) | for the payer, the base64-decoded value of the `PAYMENT-RESPONSE` header as received; for the payee, the settlement response body as its facilitator returned it |
| Receipt | `x402.receipt` (issuer: payee) | JWS format: the ASCII octets of the JWS compact serialization. EIP-712 format: the RFC 8785 form of the envelope object (`format`, `payload`, `signature`) |

All three types are already registered in the Settlement Wrapped Object Types registry. This
adapter adds no registration.

**The input is the decoded octets.** A verifier's input for each object is the octets the table
names, and the wrapped digest is over those octets. Decoding a header is a transport step. It is
checked once, when the octets are taken from the header, and it is not a property of the object.
The HTTP transport says "base64-encoded" and its examples use the standard alphabet with padding
(RFC 4648 Section 4). A header value that does not decode yields no octets: the object is then
not held. Whether the recorded payment's encoder emitted padding is **TO-CONFIRM**.

**Fields used.** From the `PaymentPayload` (specification 5.2.2; scheme Phase 1): `x402Version`;
`accepted.scheme`, `accepted.network`, `accepted.amount`, `accepted.asset`, `accepted.payTo`,
`accepted.extra.assetTransferMethod`; `payload.signature`; `payload.authorization.from`, `.to`,
`.value`, `.validAfter`, `.validBefore`, `.nonce`. From the `SettlementResponse` (5.3.2):
`success`, `errorReason`, `transaction`, `network`, `payer`, `amount`, `extensions`. From the
receipt (extension 5.2): `format`, `payload`, `signature`, and the payload members of its version.
`accepted.extra.name` and `accepted.extra.version` are transmitted but not used (§5.1).

## 5. (b) Issuers, and how they are resolved

A signature check establishes which key signed. Whether that key belongs to a party the relying
party recognizes is a decision of the relying party's trust policy. This adapter reports the two
as separate properties and never infers one from the other (extension 4.5.1 makes the same
distinction for receipts).

The relying party's policy supplies, for this adapter:

- **domains**: for each accepted (`network`, `asset`) pair, the token's EIP-712 domain: `name`,
  `version`, `chainId` and `verifyingContract`;
- **signer**: `eoa-or-contract` (the default) or `eoa`, the kind of account a payer may be (§6.1);
- **payers**: the bindings from EVM addresses to parties it recognizes;
- **receipt signers**: its extension 4.5.1 approach and what it accepts under it;
- **chain source**: where it reads the chain from (§6.4).

### 5.1 Payer: `PaymentPayload`

- **Identity on the wire.** `payload.authorization.from`, an EVM address.
- **Key recovery.** The address is recovered from `payload.signature` over the EIP-712 digest of
  the authorization (§6.1). A recovered address equal to `authorization.from` establishes that the
  holder of that address's key signed this authorization. An EVM address is not a name.
- **Resolution under the trust policy.** The relying party's policy maps the address to a party,
  or does not. When the policy binds the address to a party, `payer_trust` is `PASS`. When the
  policy holds no binding for it, `payer_trust` is `INCONCLUSIVE`. When the policy excludes the
  check, it is `NOT_CHECKED`. Recovery never establishes a binding by itself.
- **Chain and asset.** The authorization is scoped by its EIP-712 domain. The verifier takes the
  domain (`chainId`, `verifyingContract`, `name`, `version`) from its policy's entry for
  `accepted.network` and `accepted.asset`, never from transmitted values such as
  `accepted.extra.name` and `accepted.extra.version`. When the policy has no entry for that pair,
  `asset_trust` is `INCONCLUSIVE` and `payer_signature` is `NOT_CHECKED`. So a changed `network`
  label alone fails the join with the settlement response or the chain lookup, not the signature.
  The domain `name` and `version` of the token used in the recorded payment are **TO-CONFIRM**.

### 5.2 Facilitator: `SettlementResponse`

- **Identity on the wire.** None. The settlement response does not name the facilitator, and it
  carries no signature or key identifier. Facilitator identity is not cryptographic.
- **What the payer holds.** The octets of a header returned by the resource server, over whatever
  channel carried the HTTP response. Attribution to the resource server's origin rests on that
  channel (for example TLS server authentication at the time of the exchange). It is not
  re-checkable later from the octets, and it never attributes the object to the facilitator.
- **On chain.** The transaction named by `transaction` has a sender (the account that broadcast it
  and paid gas; scheme Summary: the facilitator pays gas). A transaction lookup can report that
  sender address as detail. Mapping that address to a facilitator is the relying party's policy.
- **The chain.** The settlement authority is the chain named by `network`. The relying party
  chooses the source it reads the chain from (its own node, or a service it trusts). That choice is
  part of its trust policy.

### 5.3 Payee: receipt

- **Identity on the wire.** EIP-712 format: none in the object; the signer address is recovered.
  JWS format: the `kid` in the protected header (not checked in v0, §3).
- **Resolution.** Extension 4.5.1 requires the verifier to confirm that the signing key is
  authorized for the service at `payload.resourceUrl`, and lists approaches without mandating one:
  signing with the `payTo` key, a `did:web` document, a DNS TXT record at `_controllers.<domain>`,
  or an external key registry. The relying party's policy picks the approach. Extension 5.5 asks
  for authorization as of the receipt's `issuedAt`, with revocation treated as prospective.
- Whether the recorded payment's settlement response carried a receipt is **TO-CONFIRM**.

## 6. (c) Native verification methods

### 6.1 `PaymentPayload`: payer signature recovery

Input: the octets of §4. Steps:

1. SHA-256 over the octets is the wrapped digest. Every later step reads fields parsed from these
   same octets.
2. Parse the octets as JSON. A duplicate member name is `FAIL` for `payload_form` (profile §5.2).
3. Check the scope of §3: `x402Version` 2, `accepted.scheme` `exact`, `accepted.network` in
   `eip155`, asset transfer method `eip3009`, `payload.signature` 65 bytes. Out of scope is
   `NOT_CHECKED` for every later property of this object.
4. Build the EIP-712 typed data:
   - domain: the policy's entry for `accepted.network` and `accepted.asset` (§5.1);
   - primary type `TransferWithAuthorization(address from,address to,uint256 value,uint256
     validAfter,uint256 validBefore,bytes32 nonce)` with each member from `payload.authorization`
     (the three integers are decimal strings on the wire).

   The verifier never takes the message members from the `PaymentRequired` the server sent, from
   the settlement response, or from its own expectations.
5. Compute the EIP-712 digest and recover the signer from the 65-byte `(r, s, v)` signature. A `v`
   of 0 or 1 is normalized to 27 or 28 before recovery, as upstream implementations do.
6. When the recovered address equals `authorization.from` (compared as 20-byte values, not as
   strings), `payer_signature` is `PASS`. When it differs:
   - under signer policy `eoa`, `payer_signature` is `FAIL`;
   - under `eoa-or-contract`, it is `FAIL` when a recorded code lookup shows no code at
     `authorization.from` (§6.4), and otherwise `INCONCLUSIVE`, with detail "recovered address
     differs; `from` may be a contract account; EIP-1271 not checked".

   A `FAIL` asserts that the signature is bad. Offline, a contract account's payment cannot be
   told apart from a forgery, so the default policy does not report one as `FAIL`.

The signature covers the EIP-712 digest of the authorization, not the header octets. "Over the
as-transmitted bytes" means here that the message is rebuilt only from fields parsed out of the
retained octets, which are the same octets the wrapped digest covers. It does not mean that the
signature is over those octets.

`to` and `value` are members of the signed message. Changing either after signing makes recovery
yield another address, so `payer_signature` is `FAIL` under `eoa`, and `authorization_terms` is
`FAIL` too.

Two more checks run on the same parsed fields, each reported separately (§7):

- **Terms.** `authorization.to` equals `accepted.payTo`, and `authorization.value` equals
  `accepted.amount` (the `exact` scheme transfers exactly `amount`; scheme Phase 2 step 3).
- **Validity window.** The native rule is EIP-3009's on-chain check, strict `validAfter` < `t` <
  `validBefore`, where `t` is the block timestamp of the settling transaction from the recorded
  lookup (§6.4). Without a lookup the window is `NOT_CHECKED`. The verifier never uses the time of
  evaluation, which would fail every historical payment. A facilitator's admission margin is its
  own policy, not the native rule, and is not applied.

### 6.2 `SettlementResponse`: no native signature

There is no native check of the settlement response's signature, because it has none. The adapter
runs:

1. SHA-256 over the octets of §4 (possession).
2. Form: JSON without duplicate members; `success` a boolean; `network` a CAIP-2 identifier;
   `transaction` either `0x` followed by 64 hexadecimal characters or the empty string
   (specification 5.3.2: empty when no transaction was broadcast). Form is about parsing only.
   `success: false` is a well-formed response that states a failure, and its form is `PASS`.
3. Join with the payment payload, when both are held: `network` equals `accepted.network`;
   `payer`, when present, equals `authorization.from`.
4. Transaction lookup (online, §6.4), when `transaction` is non-empty.

Steps 2 and 3 check the response's internal consistency and its agreement with the payer's signed
authorization. They do not attribute the response to anyone (§5.2).

The stated outcome (`success`, `errorReason`) is reported as detail and settled by the chain:
`settlement_onchain` is `FAIL` when the chain shows no settlement of this authorization in the
named transaction. `success: false` with `errorReason` `settlement_pending` is non-terminal
(specification 9): the transaction may still confirm.

### 6.3 Receipt: payee signature

For payload version 1, extension 5.5 is the method, unchanged, for the EIP-712 format: domain
`name` "x402 receipt", `version` "1", `chainId` 1 (extension 3.2: the chain id is fixed and does
not name the payment network); the version 1 `Receipt` type of extension 5.3; `receipt.payload`
used exactly as transmitted, never rebuilt from surrounding x402 context; recover the signer
address. JWS receipts are `NOT_CHECKED` in v0.

Payload version 2 is defined by two open pull requests that are not compatible with each other.
Both use payload `version` 2:

| | #3186 (`responseHash`) | #3140 (`contentHash`) |
|---|---|---|
| EIP-712 domain `version` | "1" | "2" |
| Fields added to `Receipt` | `responseHash`, `responseHashAlg`, `responseHashEncoding` | `commitmentId`, `settlementUnbound`, `contentHash`, `contentHashAlg`, `requestHash`, `receiptRef` |
| Hash encoding | `0x`-prefixed | hexadecimal |
| What the content hash covers | `raw`: response body octets after removing content encoding; or `jcs`: RFC 8785 form of a JSON response | the decoded HTTP entity body (after removing content encoding); no RFC 8785 form |
| Settlement binding | the version 1 `transaction` field, optional | exactly one of `transaction`, `commitmentId`, `settlementUnbound: true` |

This adapter declares both and picks neither. The two field sets are disjoint, so the payload's own
member names select the variant: a version 2 payload that carries the #3186 fields is checked under
#3186's types and domain; one that carries the #3140 fields is checked under #3140's. The `detail`
of every receipt report names the variant and the pull request head commit of §1. A version 2
payload that matches neither field set, or both, is `NOT_CHECKED` (unsupported version). The
relying party's policy may decline version 2 receipts until one variant is merged. They are then
`NOT_CHECKED` as excluded by policy. When either variant merges, a later revision of this
adapter cites the merged text and drops the other.

The content binding of either variant is a separate property (`delivery_binding`, §7). It needs
the response body octets. The receipt does not carry them.

### 6.4 Settlement on chain: recorded lookups

When `transaction` is non-empty, the verifier reads, from the chain named by `network`, through
the source its policy names:

1. the transaction exists and its execution status is success;
2. a `Transfer(from, to, value)` event emitted by `accepted.asset` with `from`, `to` and `value`
   equal to those of the payer's authorization;
3. an EIP-3009 `AuthorizationUsed(authorizer, nonce)` event emitted by `accepted.asset` with
   `authorizer` equal to `authorization.from` and `nonce` equal to `authorization.nonce`;
4. the timestamp of the transaction's block, for the validity window (§6.1).

Item 3 ties the on-chain transfer to this specific signed authorization, not merely to a transfer
of the same amount between the same addresses.

A code lookup at `authorization.from` (the account's code, empty for an externally owned account)
is recorded the same way, and decides a recovered-address mismatch under `eoa-or-contract`
(§6.1).

Both lookups are online checks (profile §7.1). Offline, `settlement_onchain` and
`authorization_window` are `NOT_CHECKED`. Vectors carry no chain endpoint. A vector supplies the
lookups as a recorded input, labelled as the relying party's observation, in the shapes of the
transaction receipt and block that a chain node returns. The transaction hash, block and event
values of the recorded Base Sepolia payment are **TO-CONFIRM**.

## 7. (e) Per-property results

Each row is one check. A verifier reports it as a `native_check` report (profile §7.2) in the
vocabulary of profile §7.1, with the check's name and its object's wrapped type in `detail`:
`{"property": "native_check", "status": …, "method": …, "detail": {"check": …, "object": …}}`.
Per-check property names are left to a later profile revision (Open point A-2).

| Check | Object | `method` (as reported) | `PASS` | `FAIL` | `NOT_PRESENT` | `NOT_CHECKED` | `INCONCLUSIVE` |
|---|---|---|---|---|---|---|---|
| `payload_form` | `x402.payment-payload` | `x402 v2 PaymentPayload: JSON parse of the registered octets, no duplicate members` | parses | does not parse, or has a duplicate member | no payment payload octets held | — | — |
| `payer_signature` | `x402.payment-payload` | `EIP-712 TransferWithAuthorization (EIP-3009), domain from policy, secp256k1 recovery, v 0/1 normalized to 27/28` | recovered address equals `authorization.from` | it does not, under policy `eoa` or with a recorded code lookup showing no code at `from` | `payload.signature` or a required authorization field absent | out of scope (§3), or no policy domain for the pair | it does not, under `eoa-or-contract`, without a code lookup showing no code |
| `payer_trust` | `x402.payment-payload` | `relying party policy <id>` | the policy binds `authorization.from` to a party | the policy rejects that address | — | excluded by policy | the policy holds no binding |
| `asset_trust` | `x402.payment-payload` | `relying party policy <id>` | the policy has a domain for `accepted.asset` on `accepted.network` | the policy rejects it | — | excluded by policy | the policy has no entry |
| `authorization_terms` | `x402.payment-payload` | `x402 exact: authorization.to = accepted.payTo, authorization.value = accepted.amount` | both hold | either does not | a member absent | out of scope (§3) | — |
| `authorization_window` | `x402.payment-payload` | `EIP-3009 validAfter < t < validBefore, t = block timestamp of the settling transaction from the recorded lookup` | `t` strictly inside | `t` outside | `transaction` empty | offline | — |
| `settle_response_form` | `x402.settle-response` | `x402 v2 SettlementResponse: JSON parse, 5.3.2 member types` | well-formed, whatever `success` states | not well-formed | no settlement response octets held | — | — |
| `settle_response_join` | `x402.settle-response` | `x402 v2: network = accepted.network, payer = authorization.from` | both agree (`payer` agrees, or is absent) | either disagrees | the payment payload is not held | — | — |
| `settle_response_signature` | `x402.settle-response` | `none: x402 v2 SettlementResponse is unsigned` | — | — | always: there is no signature to check | — | — |
| `settlement_onchain` | `x402.settle-response` | `transaction lookup on the accepted network: status, Transfer, AuthorizationUsed` | items 1 to 3 of §6.4 hold | the transaction is absent or failed on that chain, or an event does not match | `transaction` empty | offline | the source could not decide (for example not yet final under the policy, or `settlement_pending` still unconfirmed) |
| `receipt_signature` | `x402.receipt` | `x402 offer-receipt EIP-712 signature: payload version 1, or version 2 under #3186 or #3140 by member names` | a signer is recovered from a valid signature | the signature is malformed | no receipt in `extensions["offer-receipt"].info.receipt` | JWS format, or an unsupported payload version or variant (§6.3) | — |
| `receipt_signer_authorized` | `x402.receipt` | `x402 offer-receipt 4.5.1 signer authorization under the relying party's policy` | the key is authorized for `payload.resourceUrl` as of `issuedAt` | the policy shows it was not | no receipt | excluded by policy | the approach could not resolve the key's status at `issuedAt` |
| `delivery_binding` | `x402.receipt` | `#3186 responseHash or #3140 contentHash, SHA-256` | the recomputed hash equals the signed one | it does not | no receipt, no hash in it, or the body octets not held | version 1 receipt, or variant not supported | — |

Rows that depend on the relying party's policy (`payer_trust`, `asset_trust`,
`receipt_signer_authorized`) name the policy in `method`. `settlement_onchain` names the chain
source in `detail`.

`settle_response_signature` is always `NOT_PRESENT`. The adapter reports it so that a reader never
mistakes a well-formed settlement response for a signed one.

## 8. (d) Predicates supported

The adapter supports exactly these predicates. Each lists the checks that must be `PASS`.

| | Predicate | Requires `PASS` on |
|---|---|---|
| **X1** | The holder of the key for address `F` signed an EIP-3009 authorization to transfer `V` atomic units of the token at `A` on chain `N` to `T`, valid between `validAfter` and `validBefore`, with nonce `n`. | `payload_form`, `payer_signature` |
| **X2** | As X1, and the authorization matches the payment terms the payer's payload states it accepted (`payTo`, `amount`). | X1, `authorization_terms` |
| **X3** | That authorization was executed on chain `N` in transaction `H`, inside its validity window. | X1, `settle_response_form`, `settlement_onchain`, `authorization_window` |
| **X4** | The payee, through a key authorized for the service at `resourceUrl`, states that it received payment from `payer` for `resourceUrl` at `issuedAt` (and, when present, in transaction `H`). | `receipt_signature`, `receipt_signer_authorized` |
| **X5** | As X4, and the payee signed a digest of the response body the verifier holds (version 2 receipts, under the variant named). | X4, `delivery_binding` |

`payer_trust` and `asset_trust` are what connect X1 to X3 with a named party and an accepted asset.
A requirement that names a party needs them `PASS` as well.

What the adapter does **not** support:

- that the facilitator issued, or agrees with, the settlement response. The response is unsigned.
  For it, the adapter supports only possession of its octets and the transport-level provenance of
  §5.2 (FR-20). `H` reaches X3 through the settlement response only as a pointer. X3 rests on the
  chain lookup, not on the response;
- that the resource was delivered, or that the payer received any content. X5 is the payee's
  signed statement about a digest, as both proposals say. It is not the payer's acknowledgment;
- that the amount matched a signed offer. The `accepted` terms in the payload are the payer's
  statement of what it accepted. A signed offer (`x402.offer`) is outside this revision;
- anything about a party beyond what the relying party's policy binds to an address or key.

**What x402 would need to add for a native check of the settlement response.** A facilitator
signature over the `SettlementResponse`: a defined signing input (for example a JWS over the
response, or an EIP-712 type for it), a key identifier in the object, and a way to resolve the
facilitator's key (for example a key published through the facilitator's `GET /supported`
response or a DID document). With that, the settlement response would have an issuer that a
verifier could check, and X3 could cite the facilitator's statement as well as the chain. The
receipt of the Offer and Receipt Extension does not fill this gap: it is signed by the resource
server, not the facilitator.

### 8.1 Mapping to an Evidence Result

A `native_check` `PASS` or `FAIL` maps by the profile's §8.1 rows unchanged. Two examples:

- A requirement that **is** a check, "the payer signed this transfer authorization":
  `payer_signature` `FAIL` in an otherwise verified Artifact is row 5, `SATISFIED`, verdict
  `not_met`.
- A requirement the check only **supports**, "the resource was paid for": the same `FAIL` is
  row 6, `INSUFFICIENT`, verdict `not_evaluable`, unless other evidence settles it.

Profile §8.1 has no row for a `native_check` that is neither `PASS` nor `FAIL`. Such a status is
mapped as profile §8.1 rows 3-4 pending a profile row:

- `NOT_PRESENT`, when the requirement is or rests on that check: `INSUFFICIENT`, sufficiency
  `INSUFFICIENT`, verdict `not_evaluable`;
- `NOT_CHECKED` or `INCONCLUSIVE`: `UNKNOWN`, sufficiency `UNKNOWN`, verdict `not_evaluable`;
- never `met` or `not_met`.

`settle_response_signature` `NOT_PRESENT` never counts against a requirement that does not rest on
it. It records that no facilitator signature exists to rely on.

## 9. Vectors

`vectors/adapters/x402/`, regenerated byte for byte by
`python/scripts/generate_adapter_x402_vectors.py`, with `SHA256SUMS`. Each case's input is the
decoded octets of each wrapped object (§4), with the header values as informative side files, the
relying party's policy, and the recorded lookups (§6.4).

- **`positive`**: an `exact`/`eip3009` payment on Base Sepolia under the default signer policy.
  Every check with an input is `PASS`, `settle_response_signature` is `NOT_PRESENT`, and the
  receipt checks are `NOT_PRESENT` (no receipt).
- **`native-check-fails`**: the same payload with `authorization.value` changed after signing,
  under signer policy `eoa`. `payer_signature` and `authorization_terms` are `FAIL`, and so is
  `settlement_onchain`, because the recorded `Transfer` no longer matches. Profile §8.1 row 5
  applies to a requirement that is the signature check, and row 6 to one it supports.

**Constructed, not recorded.** Until the recorded Base Sepolia payment is available, both cases
are built from a payload signed with a published development key: the first default account that
Hardhat Network and Foundry anvil derive from the mnemonic `test test test test test test test
test test test test junk` (address `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`). The corpus README
names the key and its source. No real or funded key is in the corpus. The token domain is the one
the x402 v2 specification's own example uses (5.1.1, 5.2.1); that example's signature recovers to
its stated payer under it. The recorded payment replaces the positive case when it arrives, and the
**TO-CONFIRM** items close from its octets.

## 10. Out of scope for v0

The signed offer (`x402.offer`); x402 version 1 (§3.1); schemes other than `exact`; networks
outside `eip155`; the `permit2` and `erc7710` transfer methods; contract-account signatures; JWS
receipts; the MCP and A2A transports, which carry the same objects in other places; the
`batch-settlement` scheme, where a transaction hash is not unique to one payment
(`draft-mih-agent-settlement-records-00`, Initial Types, notes).

## 11. Open points

- **A-1** The registered octet definitions of `x402.payment-payload` and `x402.settle-response`
  name the version 2 headers only. Version 1 carries the same objects in `X-PAYMENT` and
  `X-PAYMENT-RESPONSE`. A registry update could name both, or version 1 could stay unsupported.
- **A-2** The profile defines one `native_check` property per foreign object (§7.2). For v0 this
  adapter reports each named check as `native_check` with its name in `detail`. A later profile
  revision could adopt per-check property names.
- **A-3** Receipt payload version 2 has two incompatible open proposals (§6.3). This adapter
  selects by member names until one is merged.
- **A-4** Profile §8.1 has no row for a `native_check` that is `NOT_PRESENT`, `NOT_CHECKED` or
  `INCONCLUSIVE`. §8.1 here maps them as rows 3-4 until a profile revision adds one.
- **A-5** Every **TO-CONFIRM** item above: the base64 padding of the recorded headers (§4); the
  token's EIP-712 domain `name` and `version` (§5.1); whether a receipt was present (§5.3); the
  transaction hash, block and event values (§6.4).
