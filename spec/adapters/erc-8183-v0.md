# ERC-8183 Adapter Profile — v0

**Status.** Informational adapter declaration, kept in this repository. It is not part of any
Internet-Draft revision, changes no posted draft and registers nothing. It defines how an
ERC-8183 (Agentic Commerce) job carries the judge record that decided it, and it declares, for the
job's on-chain objects and that record, the five items an adapter for a foreign object declares
(`spec/adapters/README.md` §1). Its vectors are in `vectors/adapters/erc-8183/` (§10).

ERC-8183 escrows a job between a client and a provider. One evaluator, fixed when the job is
created, ends it with `complete` or `reject`, each carrying a `bytes32 reason` that the EIP calls
"an optional attestation commitment" and gives no format. This profile gives it one: `reason` is
the Capsule ID of a sealed `evaluation-report/v1` (`spec/judge-record-family-v1.md` §2, cited as
JF) that judged the job's deliverable against the Evidence Contract the job named when it was
created. A third party can then check the verdict from the chain and the record alone.

The profile adds no protocol, no record type, no verdict value and no registry entry, and it
changes neither ERC-8183 nor its reference contract. It is evidence only: it has no oracle, no
on-chain judge, no hook or evaluator contract, no challenge window, bond or arbitration, and no
score.

## 2. The answer in brief

| Step | Who | What this profile fixes |
|---|---|---|
| `createJob` | client | `description` names the Evidence Contract and its digest (§6.1). The question is fixed before anyone is paid or judged |
| `submit` | provider | `deliverable` is the Capsule ID of the provider's sealed capsule for the work (§6.2) |
| `complete` or `reject` | evaluator | the evaluator seals one `evaluation-report/v1` with one case that cites the deliverable, and `reason` is its Capsule ID (§6.3). `met` is `complete`, `not_met` is `reject` (§6.4) |
| no call; `claimRefund` after `expiredAt` | evaluator; anyone | `not_evaluable` and `out_of_scope` make no call. ERC-8183's own refund path ends the job (§6.4) |

A verifier reads the job and its events from the chain, fetches the report by its Capsule ID, and
reports seven checks (§7, §8). The evaluator's identity comes from its own transaction. This
revision does not bind the key that signed the report to the evaluator's address (§12, E-1).

## 3. Scope of v0

| Dimension | Supported in v0 | Otherwise |
|---|---|---|
| Contract | an ERC-8183 kernel with the reference contract's `getJob`, `JobFunded`, `JobSubmitted`, `JobCompleted`, `JobRejected` and `JobExpired` | other interfaces: `NOT_CHECKED` |
| Network | `eip155:*` (CAIP-2) | any other namespace: `NOT_CHECKED` |
| Hook | `hook` is `address(0)` | a job with a hook: the checks run unchanged, and the hook's effects are outside this profile (§11) |
| Report | one `evaluation-report/v1` with exactly one case | more than one case: `verdict_call` `FAIL` (§7) |
| Report capsule | format 4, `canonicalization_id` `jcs`, with a Producer Envelope | anything else: `capsule_verifies` `NOT_CHECKED` |

`NOT_CHECKED` means the input is present and the verifier did not run the check (IP §7.1, cited
from `spec/interop-profile-v0.md`). It never reads as a failure of the job.

## 4. (a) Native objects and their formats

| Object | Source | Members used |
|---|---|---|
| The job | `getJob(jobId)` on the job's contract | `client`, `provider`, `evaluator`, `description`, `expiredAt`, `status`, `hook` |
| `JobFunded(jobId, client, amount)` | the contract's log | the event itself (§7 step 1) |
| `JobSubmitted(jobId, provider, deliverable)` | the contract's log | `deliverable` |
| `JobCompleted(jobId, evaluator, reason)` | the contract's log | `evaluator`, `reason` |
| `JobRejected(jobId, rejector, reason)` | the contract's log | `rejector`, `reason` |
| `JobExpired(jobId)` | the contract's log | the event itself |
| The report capsule | fetched by Capsule ID | the sealed Capsule, its Producer Envelope, and its committed payload |

A job is named by its contract and id: the CAIP-10 account of the contract
(`eip155:<chainId>:<address>`) and `jobId` as a decimal integer. The chain objects are read as
recorded lookups, the relying party's observation through the chain source its policy names, in
the shapes a chain node returns, as x402-v0 §6.4 does for its settlement. `description` is read
from `getJob`: the reference contract has no setter for it, so it is the value `createJob` stored.

The report capsule is three objects, carried together:

- the Capsule, a JSON object, whose Capsule ID is SHA-256 over JCS of the Capsule without
  `capsule_id`, `signature` and `key_id` (`draft-mih-scitt-agent-action-capsule-06`, cited as
  draft-06, Identity and parties);
- its Producer Envelope, a COSE_Sign1 over the raw 32-byte Capsule ID (draft-06, Producer
  Envelope wire profile);
- its payload, the JF `evaluation-report/v1` record, which the Capsule commits as
  `model_attestation.compute_attestation.agent_input_digest`, the JSON-DIGEST of the record
  (draft-06, Conventions and Definitions).

## 5. (b) Issuers, and how they are resolved

- **Evaluator.** The account that sent the `complete` or `reject` transaction. The reference
  contract reverts unless the sender is the job's `evaluator` (Submitted, Funded) or, for a
  `reject` while Open, its `client`. `JobCompleted` names `job.evaluator`, and `JobRejected` names
  the sender. Whether that address belongs to a party the relying party recognizes is its trust
  policy's decision, as for any EVM address (x402-v0 §5.1).
- **Report signer.** The Ed25519 key in the Producer Envelope's `kid`. The envelope proves which
  key signed the Capsule ID. Whether that key belongs to the evaluator is not checked in v0 (§12,
  E-1).
- **Provider and client.** Named by `getJob`. This profile checks no statement of theirs beyond
  `deliverable` and `description`, which their own transactions wrote.
- **The chain.** The relying party chooses the source it reads the chain from. That choice is part
  of its trust policy.

## 6. The binding

### 6.1 The question: `description`

The client MUST write, as the first line of `description`, exactly:

```
<contract_ref> sha256:<64 lowercase hexadecimal digits>
```

`<contract_ref>` is the Evidence Contract version as `<contract_id>@<version>` (the same
value the report's `contract_ref` carries, by JF's `contract_ref` convention), and the hexadecimal digits are its `contract_digest`:
SHA-256 over UTF-8 of JCS of the contract version document (IP §11.1.2). The first line is every
octet of `description` before its first line feed (U+000A), or all of it when it has none. It
carries no carriage return and no trailing space. Anything after the first line feed is free text
for people, and a verifier ignores it.

The line is never split or parsed. A verifier builds the expected prefix from the report (§7 step
4) and compares octets. A JF `contract_ref` holds no white space and exactly one `@` (the JF
schema's pattern `^[^@\s]+@[^@\s]+$`), so it never holds a line feed and the first line always
carries it whole. An Evidence Contract whose `id` or `version` holds white space or `@` has no JF
`contract_ref` and cannot be named by this profile.

### 6.2 The deliverable: `deliverable`

The provider MUST submit as `deliverable` the 32 octets of the Capsule ID of its sealed capsule for
the work. A Capsule ID leaves out the Producer Envelope's signature, so it is not the SHA-256 of
the sealed file as stored: a stranger who hashes the file gets another value. It is the same 32
octets a JF citation of that capsule carries as `digest`.

### 6.3 The verdict: `reason`

The evaluator MUST seal exactly one `evaluation-report/v1` for the job, in which:

- `contract_ref` is the job's, the `<contract_ref>` of §6.1;
- `cases` has exactly one case;
- that case's `acts` hold a citation whose `digest_alg` is `SHA-256` and whose `digest` is the
  job's `deliverable` in lowercase hexadecimal;
- `epistemic_type` is `semantic_judgment` and `judge_pin` names the judge, as JF §2 requires.

When the evaluator calls `complete` or `reject`, `reason` MUST be the 32 octets of that report
capsule's Capsule ID. The report MUST be retrievable by that Capsule ID, with its Producer Envelope
and payload, by whoever the relying party's policy expects to check it. Where it is published is
outside this profile.

### 6.4 Verdict to call

| Case `verdict` | The evaluator |
|---|---|
| `met` | calls `complete(jobId, reason, optParams)` |
| `not_met` | calls `reject(jobId, reason, optParams)` |
| `not_evaluable` | MUST NOT call `complete` or `reject`. The job ends by `claimRefund` after `expiredAt` (`JobExpired`) |
| `out_of_scope` | MUST NOT call `complete` or `reject`, as for `not_evaluable`. JF §2 limits `out_of_scope` to a requirement whose contract allows it |

A record that could not judge the work must not settle it. When evidence was not enough to judge,
no call states an outcome, and ERC-8183's non-hookable refund returns the escrow.

A `not_evaluable` or `out_of_scope` job therefore has no on-chain commitment to its report: no
evaluator transaction names it. Its report is still sealed and published, and §7 checks it
against the job, but nothing on the chain binds it to the evaluator. A verifier says so (§9, E3).

## 7. (c) The verification method

Input: the job's recorded lookups (§4) and, when held, the report capsule. The verifier runs the
checks in this order. Each is reported under §8.

1. **`is_evaluation`.** Find the job's terminal event. `JobCompleted` is an evaluation when its
   `evaluator` equals the job's `evaluator` (addresses compared as 20-octet values). `JobRejected`
   is one when its `rejector` equals the job's `evaluator` and a `JobFunded` or `JobSubmitted`
   event of the job precedes it: the job had left Open. The reference `submit` accepts an Open job
   with a zero budget, so a job can reach Submitted without `JobFunded`. A `JobRejected` with no such
   event before it is the client's rejection while Open, not an evaluation, even when the job's
   `evaluator` is its `client` (ERC-8183 Roles allows that). It and any other mismatch are `FAIL`,
   and the verifier reads no report for it. `JobExpired`, or no terminal event, has no call:
   `NOT_PRESENT`.
2. **`reason_binding`.** For a call, `reason` as lowercase hexadecimal equals the Capsule ID the
   verifier recomputes over the held Capsule. A `reason` of `bytes32(0)` names no report:
   `NOT_PRESENT`. With no call, there is no `reason`: `NOT_PRESENT`, and the verifier checks the
   report it was handed for the job by the remaining checks.
3. **`capsule_verifies`.** The held Capsule is format 4 with `canonicalization_id` `jcs`; its
   carried `capsule_id` equals the recomputed one; its Producer Envelope verifies over that
   Capsule ID (draft-06, Class 1 verification, "For each Producer Envelope"); the held payload's JSON-DIGEST equals
   `model_attestation.compute_attestation.agent_input_digest`; and the payload is a valid JF
   `evaluation-report/v1` (`schemas/judge/evaluation-report-v1.json`). A Capsule of another format
   or canonicalization is `NOT_CHECKED` (§3), and so is check 2 for it. A report held without its
   envelope or payload is `NOT_PRESENT`.
4. **`contract_binding`.** Let `P` be UTF-8 of the report's `contract_ref` followed by the eight
   octets ` sha256:`. The first line of `description` (§6.1) is `P` followed by exactly 64
   lowercase hexadecimal digits and nothing else.
5. **`contract_digest`.** Run only when check 4 is `PASS`. When the verifier holds the contract version document whose
   `<contract_id>@<version>` is the report's `contract_ref`, SHA-256 over UTF-8 of its JCS equals
   the 64 digits of the first line. Without that document the check is `NOT_CHECKED`.
6. **`deliverable_cited`.** The job has a `JobSubmitted` event, and a case of the report has an
   `acts` citation with `digest_alg` `SHA-256` whose `digest` is `deliverable` in lowercase
   hexadecimal. A job with no `JobSubmitted`, such as one an evaluator rejected while Funded, has
   no deliverable to cite: `NOT_PRESENT`.
7. **`verdict_call`.** The report has exactly one case, and its verdict agrees with how the job
   ended (§6.4): `met` with `JobCompleted`; `not_met` with an evaluator's `JobRejected`;
   `not_evaluable` or `out_of_scope` with `JobExpired`. Every other pairing, and a report with more
   than one case, is `FAIL`. A job with no terminal event has not ended: `NOT_CHECKED`, since the
   evaluator may still call.

When check 3 is not `PASS`, checks 4 to 7 are `NOT_CHECKED`: an unverified record is never read for
its content. When check 1 is `FAIL`, checks 2 to 7 are `NOT_CHECKED`. When check 1 is
`NOT_CHECKED` or `INCONCLUSIVE` (offline, unsupported, or not yet final), every check that reads
the job, 2 and 4 to 7, is `NOT_CHECKED`: there is no settled job to compare with. Check 3 still
runs on the report alone.

## 8. (e) Per-property results

Each row is one check. A verifier reports it as a `native_check` report (IP §7.2) with the check's
name and the job in `detail`:
`{"property": "native_check", "status": …, "method": …, "detail": {"check": …, "job": {"contract": …, "job_id": …}}}`,
as x402-v0 §7 does. Per-check property names are left to a later profile revision (x402-v0
Open point A-2).

| Check | `method` (as reported) | `PASS` | `FAIL` | `NOT_PRESENT` | `NOT_CHECKED` | `INCONCLUSIVE` |
|---|---|---|---|---|---|---|
| `is_evaluation` | `ERC-8183 terminal event, recorded lookup: JobCompleted, or JobRejected by job.evaluator after JobFunded or JobSubmitted` | an evaluator's call | a client's rejection while Open, or an event whose address is not the job's evaluator | no call (`JobExpired`, or no terminal event yet) | unsupported contract or network (§3), or offline | the source could not decide, for example the event not yet final under the policy |
| `reason_binding` | `reason = Capsule ID (SHA-256 over JCS) of the held report capsule` | equal | not equal | no call, `reason` zero, or no report held | check 1 `FAIL`, `NOT_CHECKED` or `INCONCLUSIVE`, or unsupported capsule format (§3) | — |
| `capsule_verifies` | `AAC format 4 Capsule ID, Producer Envelope (COSE_Sign1 EdDSA), agent_input_digest = JSON-DIGEST(payload), JF evaluation-report/v1` | all hold | any does not | no report capsule, envelope or payload held | unsupported capsule format (§3), or check 1 `FAIL` | — |
| `contract_binding` | `first line of description = UTF-8(contract_ref) " sha256:" 64 hex, octet compare` | it matches | it does not | — | check 1 `FAIL`, `NOT_CHECKED` or `INCONCLUSIVE`, or check 3 not `PASS` | — |
| `contract_digest` | `SHA-256 over JCS of the contract version document = the line's digest` | equal | not equal | — | the verifier does not hold the document, check 1 `FAIL`, `NOT_CHECKED` or `INCONCLUSIVE`, or check 3 or 4 not `PASS` | — |
| `deliverable_cited` | `one case's acts cite deliverable by SHA-256 digest` | cited | not cited | no `JobSubmitted` | check 1 `FAIL`, `NOT_CHECKED` or `INCONCLUSIVE`, or check 3 not `PASS` | — |
| `verdict_call` | `one case; met = complete, not_met = reject, not_evaluable or out_of_scope = JobExpired` | agrees | disagrees, or more than one case | — | no terminal event yet, check 1 `FAIL`, `NOT_CHECKED` or `INCONCLUSIVE`, or check 3 not `PASS` | — |

`contract_digest` is reported apart from `contract_binding` so that a verifier without the
contract document can still check that the report answers the job's question. A `NOT_CHECKED`
`contract_digest` alone never downgrades a verdict (§9.1).

## 9. (d) Predicates supported

The adapter supports exactly these predicates. Each lists the checks that must be `PASS`.

| | Predicate | Requires `PASS` on |
|---|---|---|
| **E1** | The job's evaluator, by its own transaction, committed to report `R`: a verified `evaluation-report/v1` whose one case judged the job's deliverable `D` against contract `C` with verdict `V`, and the call agrees with `V`. | `is_evaluation`, `reason_binding`, `capsule_verifies`, `contract_binding`, `deliverable_cited`, `verdict_call`; and `contract_digest` not `FAIL` |
| **E2** | As E1, and `C` is the contract version document with the digest the client fixed at `createJob`. | E1, `contract_digest` |
| **E3** | Report `R` is a verified `evaluation-report/v1` whose one case judged deliverable `D` against contract `C` as `not_evaluable` or `out_of_scope`, and the job expired without an evaluator's call. No transaction of the evaluator binds `R`. | `capsule_verifies`, `contract_binding`, `deliverable_cited`, `verdict_call` (which requires `JobExpired`), with `is_evaluation` and `reason_binding` `NOT_PRESENT`; and `contract_digest` not `FAIL`. A job with no terminal event has not ended, and E3 does not hold for it |

What the adapter does **not** support:

- that the report's signer is the evaluator. The evaluator's address and the envelope's key are
  separate, and v0 binds neither to the other (E-1);
- that the verdict is right. E1 shows what was asked, what was read, which judge answered and how
  the job ended. Whether the judge judged well is for a later adjudication (JF §6), not this check;
- that the deliverable's content is what the job wanted. `deliverable_cited` shows that the report
  judged the capsule the provider submitted, not what that capsule says;
- for E3, that the evaluator made or stands behind the report.

### 9.1 Mapping to an Evidence Result

A `native_check` `PASS` or `FAIL` maps by IP §8.1 unchanged, and a `NOT_PRESENT`, `NOT_CHECKED` or
`INCONCLUSIVE` as `spec/adapters/README.md` §3 says (IP §8.1 rows 3 and 4 until a profile row is
added), with one exception: a requirement that rests on E1 does not rest on `contract_digest`, so
`contract_digest` `NOT_CHECKED` leaves it where E1 puts it. A `contract_digest` `FAIL` is
different: the job fixed other contract bytes under the same `contract_ref`, so E1 and E3 do not
hold. A requirement that names E2 rests on `contract_digest` as on any other check.

For E3, `is_evaluation` and `reason_binding` are `NOT_PRESENT` by design. A requirement that rests
on E3 does not rest on either.

## 10. Vectors

`vectors/adapters/erc-8183/`, regenerated byte for byte by
`python/scripts/generate_adapter_erc8183_vectors.py`, with `SHA256SUMS`, and checked by
`python/tests/test_adapter_erc8183_vectors.py`, which recomputes every check with its own code.
Each case carries the job's recorded lookups (`getJob` and the events), the report capsule with
its Producer Envelope and payload, the deliverable capsule, whether the verifier holds the
contract document, and the expected status of each check. No chain is read.

- **Pass:** `met-complete` (E1 and E2), `met-complete-no-contract-document` (E1, `contract_digest`
  `NOT_CHECKED`), `not-met-reject` (E1, E2), `not-evaluable-refund` and `out-of-scope-refund` (E3).
- **MUST reject:** `reason-digest-mismatch`, `contract-ref-mismatch`, `deliverable-not-cited`,
  `not-evaluable-with-complete`, `not-evaluable-with-reject`, `met-with-reject`,
  `not-met-with-complete`, `out-of-scope-with-complete`, `two-cases`, `reason-zero`,
  `not-evaluable-still-open`,
  `contract-digest-mismatch`, `rejected-while-funded`, `client-reject-open`,
  `client-is-evaluator-reject-open`, `bad-report-signature`, `payload-digest-mismatch`,
  `carried-capsule-id-mismatch`, `payload-not-a-report`, `report-without-envelope`.

## 11. Out of scope for v0

Hooks and `optParams`: a hook may revert or add effects, and this profile reads neither. The
ERC-2771 meta-transaction extension, where the transaction sender is a relayer. Evaluator smart
contracts, for which "the evaluator's own transaction" is a contract call. Settlement policy:
challenge windows, bonds and arbitration. The ERC-8004 Reputation and Validation registries: this
profile writes no score. Mainnet.

## 12. Open points

- **E-1** The report's signer key is not bound to the evaluator's address. A later revision could
  bind them through the evaluator's ERC-8004 registration file
  (`spec/bindings/evidence-commitment-carriers-v0.md` §5.4) or a controller binding
  (`spec/controller-binding-v0.md`).
- **E-2** A `not_evaluable` or `out_of_scope` report has no on-chain commitment (§6.4). ERC-8183
  has no call that records a reason without ending the job.
- **E-3** IP §8.1 has no row for a `native_check` that is neither `PASS` nor `FAIL`. §9.1 maps
  them as the adapter README §3 does until a profile revision adds one.
