## What these are, and are not

Each fixture is a hand-authored, illustrative EvidenceBook record (header shape per
`evidence-book-internal-spec-v3.md` §3, an internal/unpublished spec) under one of the three Buzz
Evidence Contract profiles named in `evidence-contract-internal-spec-v3.md` §7. They are **not**
machine-generated from a Python reference implementation, unlike this repository's other vector
sets (e.g. `vectors/evidence-result/`, generated by `schemas/generate_result_examples.py`). No
Python/Go/TS reference implementation of EvidenceBook records, Evidence Contract profiles, or the
`nostr-pubkey` host-principal profile exists anywhere in this repository or in `capsule-engine`
as of this draft (checked directly: no `principal_ref`, `host_principal`, or `nostr` hit in either
codebase). Writing that reference is application code, out of the `spec` lane's boundary
("specification documents only... No code" — `action-state-ops/spec/CLAUDE.md`); it is flagged as
follow-on work for the `neutral` lane once the field sets below are ratified, mirroring exactly how
`vectors/evidence-result/`'s generator/checker pair was built once *its* gate cleared.

**Every digest in every fixture here is nonetheless real**, not hand-typed: each was computed via
`agent_action_capsule.canonical.json_digest` (this repository's own `lowercase-hex SHA-256 of
UTF8(JCS(value))`) over a small labeled placeholder object (`{"label": "<description>"}`), run
ad hoc from a Python shell rather than a committed generator script — consistent with the "no code"
boundary, since nothing new was added to the package. The label for each digest is named in the
table below so the value is reproducible: `json_digest({"label": "<label>"})`.

## `buzz.moderation/v1`'s three positive records

Per the capsule-registry draft Entry 3, a `buzz.moderation/v1` requirement's
`accepted_epistemic_types` MUST include all three of `SEMANTIC_JUDGMENT`, `HUMAN_REPORT`, and
`OBLIGATION_REFERENCE` — the evidentiary basis is the **combination**, not any single record. The
three `positive-*.json` fixtures here together illustrate that combination for one moderation
action (`buzz:content-action:mod-2026-09-22-0007`); none of the three alone would satisfy the
requirement.

| File | `epistemic_type` | Carries |
|---|---|---|
| `positive-semantic-judgment.json` | `semantic_judgment` | The moderation determination (`disposition`) with evaluator/model/calibration provenance — never the moderated content itself. |
| `positive-human-report-review.json` | `human_report` | A human moderator's own review outcome over that determination. |
| `positive-obligation-reference.json` | `obligation_reference` | References to `dsa:article-17` (statement of reasons) and `dsa:article-24-5` (transparency database) — a citation, never a compliance conclusion (Evidence Contract v3 §9). |

## Negative fixtures

Each negative is a minimal mutation of its profile's positive fixture (`positive-01.json` for
`buzz.agent-job/v1` and `buzz.release/v1`; `positive-semantic-judgment.json` for
`buzz.moderation/v1`), and each is built to fail exactly one documented rule — the task's own named
violations:

| File(s) | Mutation | Rule violated |
|---|---|---|
| `*/negative-event-id-as-digest.json` (all three profiles) | `payload_commitments[0].digest` set equal to `external_event_refs[0].event_id` | The Buzz transport event id and the semantic digest MUST be two distinct fields, never one (EvidenceBook v3 §14; capsule-registry drafts, common rule across Entries 2–4) |
| `buzz.moderation/v1/negative-message-text-present.json` | `judgment.moderated_text` added, carrying free text | No message text in any record — digests only (task boundary) |
| `buzz.moderation/v1/negative-score-field-present.json` | `judgment.principal_trust_score` added, a numeric score | No per-user history or scores (task boundary) |

**What is and is not proven here.** These negatives document *which field, and which rule*, each
mutation is meant to violate — the same information a generated fixture's accompanying assertion
would encode. Since no validator/schema exists yet for these record shapes (see above), no
automated check currently proves a negative is rejected, or that rejection is load-bearing rather
than vacuous (the R4 standard `vectors/evidence-result/README.md` documents for that vector set).
**This is the concrete gap left for the follow-on neutral-lane task**: once the field sets are
ratified, a schema/validator pair — analogous to `schemas/evidence-result-v0.json` +
`schemas/check_evidence_result_examples.py` — should assert each negative here fails for the
documented reason and would pass if that one rule were removed.
