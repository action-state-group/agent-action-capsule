## The `evaluation-report/v1` positive fixture's tau2 lineage

`pos-oo-evaluation-report.json`'s `cases[0]` is built from two real shapes, reconciled:

- `acts[0]`'s cited content (`_tau2_case1_conversation` in the generator) is shaped like a row from
  capsule-compiler's `examples/data/tau2_airline/` conversation family:
  `{sim_id, task_id, trial, termination_reason, messages: [...]}`.
- `verdict` is the one-line rewrite of that same family's `hand_labels.json` row shape
  (`{sim_id, hand_label: bool, predicted: bool}`) onto this schema's `{case_id, verdict}`:
  `hand_label: true` → `verdict: "met"`. The generator computes this rewrite from a literal
  `_tau2_case1_hand_label = True` rather than asserting the mapping in prose only.

Neither tau2 file is vendored into this repository — capsule-compiler is a private repo outside
this lane's scope, and no judge-shaped tau2 fixture exists anywhere yet to point at directly (see
`spec/judge-record-family-v1.md` section 9). This fixture demonstrates the schema accepts data
shaped like that family's real output, via the documented one-field rewrite, without requiring
write access to a repo this task does not own.

## `check_judge_record_examples.py`'s guarantees

For each schema: the positive validates, the negative is rejected, and the rejection is proven
load-bearing (the specific schema rule is stripped in memory, the same fixture then validates
clean, and the rule is restored and re-verified red). The same script
also runs the three-way `epistemic_type` parity check (schema const × `SCHEMA_EPISTEMIC_TYPES` ×
`schemas/vendor/epistemic-types.json`) with its own mutant check.

cd agent-action-capsule   # repo root
python3 schemas/check_judge_record_examples.py
